## Blindness constraints (restated — violating these destroys the experiment)

- The sealed answer material (`key/concepts.json`, `key/answer_key.json` of key-3) and the sealed run's per-pair records (`../peer-reconciliation-test3/runs/`) were NEVER opened during this build. Hardening rationale comes only from the spec + `2026-07-20-gate-stress-probes-RESULTS.md` (TRAIN-side diagnosis).
- **Answer-blindness (custody strengthening over v0.9; hardened in round-5).** The generation controller, the verification/composition layer, and both baselines read an **answer-blind `pairs.json`** = `{count, pairs: [{pair_id, term_a, term_b}]}` — the QUESTION (which term pairs to adjudicate), never the relation classes. Two answer-leak channels are closed: (1) `pair_id` is an **OPAQUE token** `sha256(term_a || NUL || term_b)[:16]` (UTF-8, NUL = the 0x00 byte) — NOT the positional `P01–P10` that would encode the class under the harness key schema; (2) the emit order is a **seeded-but-key-independent shuffle** (sorted by the opaque id, a uniform hash), so the sequence carries no `P01–P10` class ordering. (`term_a == term_b` for jingle pairs is inherent — the jingle strings are known/orchestrator-visible and are in the exposure ledger; it is not hidden.) The relation classes (`expected`/`broader_side`) live only in the sealed key and are read by **exactly one component**, `scorer_v010.py`, at the single authorized scoring read (the SPEND, §4.2 step 9). `pairs.json` is produced by `make_pairs_manifest.py` run as an **isolated subprocess** whose only output is the blind `pairs.json` + its hash (custody-logged, phase 0.5); the orchestrator never parses the key in-process. `load_pairs` enforces a strict whitelist schema, rejects symlinks, and rejects any resolved path under a `key/` directory. The scorer joins `pairs.json` ↔ sealed key on the **term pair** (opaque id has no positional meaning).
- No LLM calls were made during the build. All self-tests are offline/deterministic.

5. ATTESTATION POINT 1 (pre-generation): STRICT verify-files (H self-checked first; fail on missing/extra runtime or corpora) + clean tree + CLI-version enforced + probe membership + v0.9-carried-artifact hash-verify (incl. isolation wrapper) + live BGE-tree recompute vs H + conformance runner; + receipt. A failure → `state:abort-before-gen`.
6. key-3 tool-arm generation (answer-blind): excerpts → checklists (H1/H2 loop) → ladders (H1/H2 loop) → conformance (DRAIN ladder regens to quiescence before each lowest-pending-index batch — no stranding) → polarity → retrieval → verify → aggregate → adaptive-1/2 → compose
7. baselines (answer-blind): A retrieve/prompts/gate(+reask), B prompts/gate(+reask)
8. **step-7 OUTPUT MANIFEST** (`attest build-output-manifest`): hash every scorer input + model output, bound to H.
9. **THE SPEND (fresh attest-2 per attempt + atomic claim + one bounded relaunch):** each attempt runs ATTESTATION POINT 2 FRESH (verify-files + recorded-artifacts + BGE + the output-manifest — every scorer input present & hash-matching), then appends a bounded `state:scoring-attempt` (max 2) with an EXPLICIT `|| exit` (a refused marker NEVER reaches the scorer). `scorer_v010.py` runs the pre-claim gate (exactly one structure:read + a uniquely-open in-range attempt + no terminal event), re-verifies its inputs against the output-manifest, appends `spend:authorized-read-claimed` UNDER THE LOCK immediately before the first key byte, reads the key, writes **AGGREGATE-ONLY** `runs/scores.json` (no per-pair / expected / pair-id lists), and appends `spend:authorized-read-complete`. A pre-read failure with attempts<2 → ONE relaunch (re-attesting first); a failure AFTER the claim → `spend:fault-after-authorized-read` (SPENT), no relaunch; after the relaunch → `state:terminated-during-gen-or-attest2-mismatch` (forfeited). Per-pair diagnostics are written to `runs/scoring/per-pair-EMBARGOED.json` ONLY under `--post-commit-receipt <addendum-commit>` (Q7 post-commit operation).

## Deviations from the spec / judgment calls (feed round-5)

1. **Answer-blind `pairs.json` split (the load-bearing custody decision) — hardened in round-5.** The spec requires the scorer to be the only component referencing the sealed key path, and step-7 generation to be "sealed-answer-material-blind," yet retrieval + verify + adaptive stages structurally need the *pairing*. Resolution: the pairing is the QUESTION (answer-blind), supplied via `pairs.json` with **opaque `sha256(terms)` ids in a key-independent shuffle** (no `P01–P10` positional class encoding) and a **strict-whitelist, symlink-safe** `load_pairs`; the ANSWER (`expected`/`broader_side`) is read only by the scorer, which joins on the term pair. The projection runs as an **isolated subprocess** (phase 0.5) emitting only the blind `pairs.json` + hash, custody-logged; the orchestrator never parses the key in-process. **Residual flagged for round-5:** for key-3 the isolated projector still *parses* the sealed `concepts.json` (which contains classes/descriptions) to extract the terms+pairing, discarding the answer — a bounded, logged read, not the SPEND. If round-5 judges even the isolated parse unacceptable, the blind `pairs.json` must be emitted by the isolated key-author at seal time instead.
2. **Parser wrapper-quote stripping (refined in round-5).** The parser strips at most one **genuinely matched** pair of surrounding double quotes — ASCII `"…"` OR curly `“…”`; **mixed** wrappers (`"…”`, `“…"`) are NOT stripped. Pinned by 4 fixtures (2 matched-strip, 2 mixed-not-stripped). A stricter "no stripping at all" variant remains possible; flagged.
3. **Conformance batch key = generation index** (not v0.9's incrementing wave counter). Implements §5's "one ordered batch per side per artifact-generation index" literally; equivalent to v0.9's waves under the driver's sequencing, but keyed to the spec's unit.
4. **`split_corpus.py` is now IN the workspace** (round-5): copied from the frozen v0.9 tree, hash-verified against the freeze-manifest recorded value (e240…), bound in H, and used by `setup_confirmatory.py` by default (the earlier operator-supplied `--split-script` deviation is dropped). **Correction to the round-5 review re `gen-community-{a,b}.md`:** these are NOT generic static files and were NOT added. `build_briefs.py` (frozen, in H) generates them PER KEY from that key's `concepts.json`; the confirmatory path generates fresh ones per conf key, and the key-3 v0.10 path does not regenerate corpora (they are frozen precondition inputs), so no static `gen-community` file is referenced. The key-3 `gen-community-{a,b}.md` recorded as 967…/22e9… in the freeze-manifest are the SEALED, key-3-specific briefs (they embed key-3's concept descriptions per `build_briefs.py`), so copying them would breach blindness — they are deliberately not in the workspace.
5. **`retrieve_xc_v010.py --no-determinism`.** Key-3 and each confirmatory draw are fresh (no prior v0.8 retrieval baseline), matching the frozen key-3 TEST harness which added the same flag; the retrieval algorithm is byte-identical to v0.9.
6. **Confirmatory draws run in a copied workspace** (`run_confirmatory.sh` copies the instrument into each conf-key dir), matching the frozen precedent (test3 = the v0.9 package copied verbatim per key), so no in-place workspace parameterization was added (that would have broken the gate byte-identity proof).

## Spec-wording amendments implied for the freeze fold (running list)

These are artifact-vs-prose divergences the artifacts resolve; the frozen spec text should be amended to match at the freeze fold (artifacts are normative, §3.6):

1. **Single-document grounding** — §3.4/§3.5's "a contiguous substring of the concatenated retrieved documents" → "a contiguous substring of at least one individual retrieved document" (a boundary-spanning span validates in no single document and must fail; per the BUG-1 fix).
2. **Checklist-exhaustion counting** — §4.1's confirmatory numerator counts a checklist configFail as **2** failed artifacts (the checklist AND its never-created ladder) against the fixed denominator 40.
3. **Projector custody step** — the answer-blind `pairs.json` is produced by an isolated-subprocess projector (phase 0.5), custody-logged and bound in H, before generation; `pair_id` is an opaque hashed token in key-independent shuffled order (no `P01–P10` positional class encoding). The projector (a) HASH-GATES the sealed source file against the recorded value in the committed `freeze-manifest.txt` before parsing (abort with nothing read on mismatch = `state:abort-before-gen`), and (b) registers a single typed `structure:read` (NON-SPEND) in the ONE authoritative locked spend log the scorer + attest read. The pairs.json schema is itself a §3.6 committed artifact, fixture-backed (`pairs_manifest` kind). The spec's custody wording (§4.3/§4.4) should name the `structure:read` typed entry as a sanctioned non-spend reader alongside the scorer's authorized read.
4. **Opaque-id formula** — the blind-manifest `pair_id` is `sha256(term_a || NUL || term_b)[:16]` (UTF-8, NUL byte 0x00); §3.6(d′) and this README's top section both use the NUL form (the delimiter-free `term_a || term_b` wording in the spec should be corrected to match).
5. **Projector-before-H ordering** — §4.2 must renumber Phase 0.5 BEFORE the H-building step and state that the projector *source* is already committed/immutable (so it runs first, then H binds both that source and its `pairs.json` output). The workspace already runs `projector → build-H`.
6. **Parser field order** — §3.6(a) says "exact field set and order," but the fixtures deliberately pin ORDER-AGNOSTIC parsing (`parse_field_order_reversed_*` expect success); §3.6(a) should read "exact field set, order-agnostic" (the prompt still states a preferred order). No code change — the artifact already parses any order.
7. **Atomic-claim spend transition** — §4.4 must describe scoring as: driver `state:scoring-attempt` (max 2) → scorer `spend:authorized-read-claimed` under the lock immediately before the first key byte → `spend:authorized-read-complete`; a pre-read failure with attempts<2 permits ONE relaunch, a claim (or attempts==2) forbids any further read; a post-claim fault is `spend:fault-after-authorized-read` (spent+invalid), never forfeited-unspent.
8. **Pinning-at-boundary (§6)** — "every Claude call by explicit pinned ID" is implemented by a frozen alias→pinned-ID translation at the `run_calls.sh` boundary (`pin_model.py`), which keeps the carried gate/staging functions and the frozen isolation wrapper byte-identical; §6 should name translation-at-boundary as the compliant mechanism.
9. **Freeze-package binding (§4.2/§8)** — H binds the ratified `PREREG.md` BYTES (`prereg_sha256`) and `recorded-cli.json` (`recorded_cli_sha256`), not a textual spec label; build-H enforces a REQUIRED inventory (refuse on any missing required file; `--runtime` = exact corpora 01..11 + pairs.json + leakcheck + key); attestation binds the `recorded-cli.json` + probe-log hashes into an integrity record and requires both inputs.
10. **Confirmatory leak execution (§4.1a)** — setup EXECUTES the frozen `leakcheck_peer.sh cross-a|cross-b|meta` over every corpus doc as part of corpus-attempt validation (a leak consumes the attempt), exactly as `run_test_v09.sh` does; and runs a per-key hash-verified `split_corpus.py` so outputs land under the key dir.
11. **Scoring relaunch + re-attestation (§4.4)** — the ONE permitted pre-read relaunch runs attestation-point-2 FRESH first; the attempt marker is capped at 2 with an executable refusal BEFORE the scorer (a restarted third attempt cannot reach it); the claim/scorer gates require a uniquely-open in-range attempt and reject any terminal state.
12. **Restart/terminal routing (§4.2/§4.3)** — H-bound phase receipts (`runs/phase-*.done`) skip verified-complete phases on restart and never regenerate a completed confirmatory key/draw; projector/probe/attestation-1 failures route to `state:abort-before-gen` (unspent+unforfeited), everything after key-3 generation begins to `state:terminated-during-gen-or-attest2-mismatch`.
13. **Step-7 output manifest (§4.2 steps 7–9)** — the complete step-7 output set (scorer inputs + model outputs) is hashed into a receipt bound to H, enforced at attestation-2, and re-verified by the scorer against every input BEFORE the claim (a missing/drifted input aborts pre-claim, unspent).
14. **Exact inventories (§4.2/§8)** — build-H enforces set-EQUALITY against a canonical `REQUIRED-INVENTORY.txt` for implementation files (rejects any extra or missing) and against the exact 01..11 corpora under `--runtime` (rejects e.g. `corpora/a/12.md`).
15. **Aggregate-only scoring output (§3.3 Q7 / §4.2 step 10)** — `scores.json` carries aggregates only (S, P, C, decision row, aggregate FP/promotion counts — no per-pair/expected/pair-id data); per-pair diagnostics are a separate post-commit export gated by an addendum-commit receipt (`--post-commit-receipt`).
