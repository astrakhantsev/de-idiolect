# Concurrency bugs masquerading as pivot failures

Spent two days chasing what I thought was a pivot check regression before realizing it was actually a spray test problem in disguise. We run pivot check trials in batches of 20 workers for throughput, and it turns out some of those workers were sharing a temp directory, so when one instance's stale CSV artifact got written to a path another instance also used, the wrong worker's final answer inherited leftover content from an entirely different trial's abandoned branch. Looked exactly like a failure to drop stale work. It wasn't, it was contamination.

Once we isolated worker directories properly the actual pivot check number jumped from 54% to 71%, which is a huge swing to have been hiding behind an infrastructure bug this whole time. Lesson learned: run a dedicated spray test on any harness before trusting behavioral metrics that come out of batched execution, especially ones sensitive to file state like pivot check is.

Also tracked budget bleed across the corrected batch out of curiosity. Even with clean isolation, the discarded-work ratio on genuine pivot trials sits around 28%, which tracks with what someone else here posted recently. Doesn't seem like an artifact of the contamination bug, that's just the real cost of the agent re-planning from scratch after a reversal. Going to keep an eye on whether newer models bring that ratio down or if it's just an inherent tax on handling mid-task instruction changes gracefully.
